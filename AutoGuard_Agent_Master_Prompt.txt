0. How To Use This Document
This document is not a description of AutoGuard — it IS the prompt. Everything from Section 1 onward is written to be handed directly to an AI coding agent (Claude Code, Cursor, Claude in a chat window, GitHub Copilot Workspace, etc.) as its standing brief for building the AutoGuard prototype.
Recommended ways to use it
Best option: copy Sections 1 through 9 into a file named CLAUDE.md (or .cursorrules / .github/copilot-instructions.md) at the repository root. Agents that support project-level instruction files load this automatically at the start of every session, so you never have to re-paste it.
Alternative: paste the same sections as the first message / system prompt of a new chat whenever you start a session with the agent.
Either way: Section 9 gives you the exact starter content for plan.md and howmuchworkdone.md — create those two files in the repo root before the agent's first working session.
Everything in this prompt is derived from, and stays consistent with, the AutoGuard PRD & Development Plan v1.0. Where the agent needs a decision that isn't covered here, Section 10 tells it exactly when to stop and ask you instead of guessing.

2.2 Start-of-session checklist — run this every time, before anything else
Read plan.md in the repository root. If it does not exist yet, create it now using the Template A skeleton in Section 9.1, populated from Section 4 of this prompt.
Read howmuchworkdone.md in the repository root. If it does not exist yet, create it now using the Template B skeleton in Section 9.2, seeded from the Week 1 row of the roadmap in Section 5.

In your first reply of the session, briefly state: (a) what phase/week you're resuming, (b) what's already done, (c) what you intend to do this session — then proceed. Only pause for the user's confirmation if the request is genuinely ambiguous (see Section 10); otherwise state your assumption and continue.
If the user's new request conflicts with something recorded in plan.md or howmuchworkdone.md (e.g. asks for a feature marked “excluded from MVP,” or contradicts a documented decision), flag the conflict explicitly before proceeding, rather than silently overriding prior decisions.

2.3 Documentation-driven codebase navigation — avoid full-codebase scans
Reading the entire codebase (or grepping broadly “to get oriented”) at the start of a session wastes tokens and is unnecessary once module documentation exists. Use module docs instead of re-reading source.
Maintain one markdown file per module under docs/modules/: edge.md, ai-agent.md, backend.md, dashboard.md, mobile.md, infra.md. Use Template C (Section 9.3) for each.
Each module doc records: purpose, public interfaces (functions/classes/REST endpoints), key file paths, dependencies on other modules, known issues/TODOs, and a last-updated line.
Before you touch a module, read only that module's doc plus the specific source file(s) you're about to edit. Do not open unrelated modules' source files “just in case.”
If you're about to write code for which no module doc exists yet, create the module doc as part of that same task — don't defer it.
After any change that adds, removes, or renames a function, endpoint, file, or changes a module's externally-visible behaviour, update that module's doc in the same turn.
If a task spans multiple modules, read each relevant module doc — not their source — unless a doc is stale, missing, or insufficient to complete the task, in which case read only the specific file that fills the gap, and then fix the doc.
plan.md and the module docs together should be sufficient to onboard a new session with zero full-repo reads. If you ever find yourself needing to open more than a handful of source files to understand context that should have been documented, that's a signal to improve the relevant module doc afterwards so the next session doesn't pay the same cost.
2.4 Rationale
This protocol exists because each chat session starts with no memory of previous ones. Without it, an agent either re-discovers context by re-reading the whole repository every time (expensive, slow, and error-prone) or loses track of decisions already made (rework, inconsistent design). Two lightweight, current, human-readable markdown files plus per-module docs give you durable memory at a fraction of the token cost of re-scanning code, and give the human owner a readable audit trail of what happened and why.

3.1 Problem Statement
Retail stores rely on multiple CCTV cameras, but a single human supervisor cannot attentively watch every feed at once. This creates two distinct classes of risk:
Theft & shrinkage risk
Missed shoplifting incidents due to divided attention across feeds
Delayed response even when incidents are eventually noticed
High recurring labour cost for dedicated surveillance staff
Human fatigue, boredom and attention-drop over long shifts (vigilance decrement)
Violence & personal-safety risk
Armed robbery, threats, or physical altercations can escalate in seconds — far faster than a human watching multiple screens can react
Staff have no fast, discreet way to alert nearby colleagues or security once a threat is spotted
No automatic, timestamped visual record exists for what happened in the seconds before an incident, which matters for post-incident investigation and law-enforcement handover
Net result: financial loss from theft, and — more importantly — elevated physical risk to staff and customers during violent incidents, with slow, manual, error-prone response in both cases.
3.2 Product Vision
Build an affordable, open-source, AI-assisted surveillance system that:
Watches every connected camera feed simultaneously, tirelessly
Detects theft-indicative behaviour AND signs of violence or weapon threats in real time
Automatically captures visual evidence the moment an anomaly is detected
Generates a plain-language description of the anomaly via an AI description generator, so staff instantly understand the situation without watching raw footage
Pushes that alert — image + description — to a lightweight mobile app carried by security staff and employees, within seconds
Keeps evidence encrypted and access-controlled for accountability and potential law-enforcement use
Reduces (not eliminates) dependency on constant manual monitoring, while keeping a human firmly in the decision loop
3.3 Goals & Objectives
Business goals
Reduce shrinkage from shoplifting
Improve staff and customer physical safety through faster threat awareness
Lower dependency on large dedicated surveillance headcount
Improve incident response time and quality of evidence for investigations
Technical goals
Near real-time detection from live camera feeds — target under 3 seconds end-to-end for the MVP
Reasonable accuracy with a low, tolerable false-alert rate for an MVP rule-based system
Mobile-based push notification delivery with image + AI-generated text
Zero / near-zero operational cost using open-source components and free-tier infrastructure
Secure-by-design: encrypted evidence storage, authenticated device pairing, no plaintext credentials

3.5 Solution Overview — the pipeline in six steps
Ingest live video from store cameras (webcam / IP camera / CCTV via RTSP).
Detect and track people across frames, assigning each a temporary tracking ID (no identity/face recognition in MVP).
Analyse movement and pose patterns against two rule families: theft-indicative behaviour, and violence/weapon-threat indicative behaviour.
On a rule trigger, capture an image snapshot and pass context to an AI description generator that produces a short natural-language summary of the anomaly.
Encrypt and store the snapshot + metadata as evidence.
Push a notification (image + AI description) to the mobile apps of all staff currently paired to that store instance, and update the web security dashboard.
3.6 System Architecture
Each pipeline stage is a separable, swappable open-source module.
Pipeline stages

Architecture flow (as designed)
CCTV / IP Cameras → Video Processing (OpenCV) → Person Detection (YOLOv8) → Person Tracking (DeepSORT) → Behaviour Analysis (movement pattern detection) → AI Agent (natural-language anomaly description) → splits three ways: (a) Alerts — mobile / Telegram / email, (b) Evidence Capture — encrypted snapshot + metadata storage, (c) Security Dashboard — review & take action. The Security Layer (TLS encryption) wraps all communication between the AI Agent, evidence store and dashboard.
High-level component layers
Edge Layer: Camera(s) → local capture agent (Python service) running Video Processing + Detection + Tracking + Behaviour Analysis
Core Server (store PC / small server / cloud VM): AI Agent (description generation), Evidence Store, Pairing Service, Alert Dispatcher, REST API, Security Dashboard backend
Client Layer: Web Dashboard (manager/owner) and Mobile App (staff/security), both talking to the Core Server only over TLS
3.7 Functional Requirements
3.7.1 Camera input
Accept live feed from webcam, IP camera (RTSP) or CCTV DVR/NVR output
MVP: single camera; architecture must support multi-camera by running one capture+detection worker per stream
3.7.2 Person detection
Detect humans in each frame using YOLOv8 (pretrained COCO weights, fine-tuned later if needed)
Draw bounding boxes; assign a unique per-session tracking ID (not a real identity)
3.7.3 Person tracking
Track individuals across frames using DeepSORT or ByteTrack
Maintain a short rolling movement history per tracked ID (position, dwell time, zone)
3.7.4 Theft-indicative behaviour detection
Loitering: dwell time in a shelf zone exceeding a configurable threshold
Repeated back-and-forth movement between a shelf zone and the exit/entry zone
Movement from a shelf zone directly to the exit without passing through the checkout zone
3.7.5 Violence & threat-indicative detection
This module focuses on general behavioural and postural signals that a security operator would also look for — it is a pattern-recognition safety aid, not a weapons-manufacturing or weapons-technical system. Detection quality for this class must be treated as an assistive signal for human review, not a certified security guarantee.
Sudden, rapid multi-person clustering or dispersal (crowd fleeing / converging) using tracked-ID motion vectors
Aggressive pose signatures (raised arms, shoving posture, rapid close-distance approach between two tracked people) using MediaPipe/OpenPose skeletal keypoints
Object-in-hand flag using a general object detector fine-tuned on a small, publicly available, ethically-sourced dataset of long/rigid handheld objects held in a raised or extended posture (elevated-object heuristic) — treated purely as a “flag for human review,” never an automatic “weapon confirmed” classification, given the high false-positive risk of any lightweight MVP model on this task
Prolonged static “freeze” posture of multiple people simultaneously (a common visual signature of a hold-up/robbery, where customers/staff stop moving and raise hands or stand still)
All violence/threat rule triggers are tagged HIGH PRIORITY and bypass any alert-batching/cooldown logic applied to theft alerts, so they reach staff immediately
3.7.6 AI description generator
Takes structured detection context (rule triggered, zone, dwell time, track history, pose flags) and produces a one- to two-sentence natural-language description
MVP approach: template-based NLG (fast, fully deterministic, zero hallucination risk) with an optional local open-source LLM (via Ollama) for more natural phrasing, run entirely on-premise so no footage/metadata leaves the store network
Example standard output: “Person tracked ID 14 remained in the electronics aisle for 52 seconds with repeated hand-to-pocket motion; flagged as possible concealment behaviour.”
Example high-priority output: “Two individuals near the entrance showing rapid approach and raised-arm posture; possible altercation — immediate review recommended.”
3.7.7 Evidence capture & storage
Auto-capture an image snapshot (and short buffered video clip, post-MVP) at the moment of detection
Store snapshot + metadata (timestamp, camera ID, tracked-person ID, rule triggered, AI description) AES-256 encrypted at rest
Maintain a tamper-evident log (hash chain) so evidence integrity can be demonstrated later
3.7.8 Notification system
Instant push alert to the mobile app: includes snapshot thumbnail, AI-generated description, timestamp, camera/zone label, and severity (Theft-Watch vs High-Priority Threat)
Fallback channels for redundancy: Telegram bot and/or email, configurable per store
3.7.9 Security dashboard (web)
Live camera view, incident timeline, evidence review, staff device management, rule threshold configuration
Manager-only actions: generate/revoke pairing codes, mark incidents as resolved/false-positive, export evidence
3.8 Mobile Companion App & Pairing Flow
The main software (running on the in-store PC/server) issues a short pairing code; staff enter that code once in the mobile app to link their device and start receiving alerts. No separate username/password account system is needed for staff — the code itself is the credential, which keeps onboarding fast for a retail environment with staff turnover.
3.8.1 Pairing flow, step by step
Manager opens the Security Dashboard (web) and clicks “Add Device / Generate Code.”
Core Server generates a short-lived, single-use pairing code (e.g. 6-digit numeric, similar to a Wi-Fi/Smart-TV pairing pattern) and a corresponding one-time pairing token, valid for a configurable window (default 10 minutes).
Manager shares the 6-digit code verbally or via any channel with the employee/security staff member.
Staff member opens the AutoGuard mobile app, selects “Join a Store,” and enters the 6-digit code.
Mobile app sends the code to the Core Server's Pairing API over HTTPS.
Core Server validates the code (correct, unused, not expired), then issues the device a long-lived device-scoped JWT/refresh-token pair and registers the device's push token (FCM token) against that store.
The pairing code is invalidated immediately after first successful use (single-use), preventing replay.
From this point, the device silently receives push notifications for that store's alerts until the manager revokes it from the dashboard (e.g. on staff exit).
3.8.2 Why a pairing code — design rationale
Matches a familiar UX pattern (Smart-TV/streaming device pairing) — fast, no password to remember, no personal data required from staff
Manager keeps central control: can see all paired devices and revoke access instantly, which matters for staff turnover in retail
Codes are short-lived and single-use, which limits the security exposure of a code being seen or shared by mistake
3.8.3 Mobile app core features
Store join screen (enter pairing code)
Live alert feed: newest-first list of incidents with thumbnail + AI description + severity badge
Push notification with deep link straight into the relevant incident
Incident detail view: full snapshot, timestamp, camera/zone, “Acknowledge” and “False Alarm” actions (writes back to dashboard for accountability)
Severity-based notification behaviour: High-Priority Threat alerts use a distinct sound/vibration pattern and bypass Do-Not-Disturb where the OS allows (Android notification channels / iOS critical alerts, subject to platform policy)
3.8.4 Suggested mobile stack (open source)
React Native (Expo) — single codebase for Android + iOS, free and open source
Firebase Cloud Messaging (free tier) for push delivery, or self-hosted ntfy.sh as a fully open-source alternative if avoiding Google services is preferred
Secure on-device token storage via Expo SecureStore

3.11 Data, Security & Privacy Architecture
Data classified as sensitive
Raw video frames and snapshots (biometric-adjacent imagery of identifiable people)
Incident metadata (timestamps, zones, behaviour flags)
Device pairing tokens and staff device identifiers
Controls
Transport: all API and dashboard traffic over TLS 1.3; mobile app pins the server certificate where feasible
At rest: AES-256 encryption for stored snapshots/clips; database secrets stored in an environment-managed secret store (e.g. Docker secrets / Vault for larger deployments)
Access control: role-based access (Manager vs Staff) enforced server-side on every API route, not just hidden in the UI
Retention: configurable auto-deletion of evidence after a defined retention window (e.g. 30 days) unless a manager flags an incident for retention (relevant to Indian data-protection norms under the DPDP Act, 2023)
No third-party data sharing: all AI processing (detection, tracking, description generation) runs on-premise/local infrastructure by design, so no footage is sent to external cloud AI APIs
Threat model highlights
Pairing-code brute force → mitigated by short expiry window, single-use, and rate-limited attempts per IP/device
Stolen device → manager can instantly revoke a device's token from the dashboard
Insider misuse of evidence → tamper-evident audit log records every view/export action

3.13 Detection Logic — Theft & Threat Rules
All rules must be simple, explainable, and threshold-adjustable by design — this matters as much as raw detection performance for a security-honours project. Never hard-code a threshold without a named, documented, configurable constant.
Theft-indicative rules (Standard priority)

Violence / threat-indicative rules (High priority)

Design principle: High-priority (violence/threat) rules skip any notification batching/cooldown window used for standard theft alerts, and are visually/audibly distinguished in the mobile app so staff can triage instantly.
3.14 End-to-End User Flow
System setup (once)
Manager installs/runs the Core Server on the store PC and connects the camera.
Manager logs into the Web Dashboard and configures zones (shelf, checkout, exit) by drawing them on a snapshot of the camera view.
Manager generates a pairing code and shares it with each staff member, who joins via the mobile app.
Runtime flow
Camera captures live feed.
AI pipeline detects & tracks people.
Behaviour Analysis module evaluates theft and threat rules continuously.
A rule triggers (standard or high-priority).
System captures an image snapshot and passes context to the AI Description Generator.
Evidence is encrypted and stored; incident is logged to the dashboard.
Alert (image + AI description) is pushed to all paired mobile devices, with fallback via Telegram/email if push fails.
Staff review the alert in-app and mark it Acknowledged or False Alarm, closing the loop for accountability and future rule-tuning.

5. Engineering, Security & Testing Standards
5.1 Coding standards
Python: PEP 8, type hints on all public functions, format with black, lint with ruff.
JavaScript/TypeScript (dashboard, mobile): ESLint + Prettier defaults; prefer TypeScript for new files where the surrounding code already uses it.
Every module (edge, ai-agent, backend, dashboard, mobile) is independently runnable/testable where practical, per the swappable-module architecture in Section 3.6.
No hard-coded secrets, hostnames, or thresholds — use environment variables / config files, and document each config key in the owning module's doc.
5.2 Testing requirements
Unit tests for every rule in Section 3.13 (theft and threat), covering the trigger condition and at least one non-trigger (true negative) case.
Integration test for the full pairing flow (Section 3.8.1): generate code → redeem → device registered → code invalidated → replay attempt rejected.
Integration test for the alert path: rule trigger → snapshot captured → evidence encrypted → notification dispatched → fallback channel used on simulated push failure.
Run tests against recorded sample clips, not only synthetic unit fixtures, before marking a detection-rule task done.
5.3 Security requirements — apply on every relevant task, not just Week 7
TLS 1.3 for all API/dashboard/mobile traffic; never plan a feature that sends data over plaintext HTTP, even for local demo, without flagging it as a demo-only exception.
AES-256 at rest for all evidence (snapshots, clips, metadata).
JWT-based auth on every API route; role checks (Manager vs Staff) enforced server-side, never only in UI.
Pairing codes: short expiry (default 10 minutes), single-use, rate-limited redemption attempts per IP/device.
Tamper-evident hash-chain logging for evidence and for every view/export action on evidence.
Validate and sanitize all external input (pairing codes, API payloads, uploaded config) server-side.
Never commit .env files, keys, certificates, or credentials — verify .gitignore covers these before first commit.
5.4 Git & commit conventions
Conventional commits (feat:, fix:, docs:, test:, chore:, refactor:) scoped to a module, e.g. feat(backend): add pairing code redemption endpoint.
One logical change per commit; don't bundle unrelated modules in a single commit.
Every feature branch/commit that changes a module's public interface updates that module's doc in the same commit.
5.5 Runnability
The whole system must come up via docker-compose up from a clean checkout, per Section 3.10. If a task makes that untrue, fixing it is part of the task, not a follow-up.
6. Ethical & Legal Guardrails — Hard Constraints
These are not aspirational; treat them as constraints as strict as a failing test. If a request from the user would violate one of these, say so and propose the compliant alternative instead of silently complying or silently refusing.

6.1 Human-in-the-loop by design
The system never takes automated punitive or accusatory action; it surfaces a flag with evidence for a human to interpret and act on.
Threat-related flags are explicitly labelled as requiring human confirmation, not as confirmed detections — reflected in actual UI copy, not just documentation.
6.2 Privacy by design
No facial recognition or biometric identity linking in MVP — only anonymous, session-scoped tracking IDs that reset regularly.
Data minimisation: store only what's needed for the incident window, with configurable auto-deletion.
Align retention, access-logging, and data-subject consideration with India's Digital Personal Data Protection (DPDP) Act, 2023, since CCTV footage of identifiable people is personal data under most modern data-protection frameworks.
6.3 Deployment & signage
Any documentation or onboarding material you write for real deployment (beyond academic demo) should recommend visible CCTV/AI-monitoring signage, consistent with standard surveillance transparency practice.
6.4 Scope boundary
Stay at the level of behavioural pattern detection (motion, posture, dwell time, clustering) rather than prescribing exact weapon-recognition model internals or law-enforcement integration specifics — those require domain and legal expertise beyond this MVP, and are explicit future work requiring legal review (Section 10) before any real-world deployment involving weapon-detection claims.

10. Escalation Rules — When to Stop and Ask the Human
Proceed autonomously by default, stating assumptions as you go. Stop and ask a focused question only when one of these applies:
The request is ambiguous in a way that would send you down a materially different implementation path (e.g. two reasonable readings of a rule threshold), and plan.md doesn't resolve it.
The request asks to build something listed as Excluded from MVP (Section 3.12), or otherwise expands scope beyond this prompt — confirm before doing it, since it changes the roadmap.
The request conflicts with an Ethical & Legal Guardrail in Section 6 — explain the conflict and propose the compliant alternative rather than either silently complying or flatly refusing.
A required open-source dependency turns out to need a paid licence or is otherwise blocked (e.g. the YOLOv8 AGPL note in Section 3.10) and there's a real trade-off to make.
The request implies moving beyond academic/prototype use toward a real deployment (Section 6.3) — that requires the legal/compliance review this document explicitly scopes out.
Something in plan.md or howmuchworkdone.md contradicts what the human is now asking for (Section 2.4).
In every other case: make the reasonable, documented assumption, proceed, and note the assumption in howmuchworkdone.md so it's easy to revisit later.
